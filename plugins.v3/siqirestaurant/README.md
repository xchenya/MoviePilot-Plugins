# 思齐餐厅（MoviePilot V3）

在 MP 内操作思齐餐厅，并由 MP 后台完成每日开业、烹饪、上菜和按需补货。原生 Vue 面板，无需 iframe；关闭页面后托管继续运行。

## 设置

1. 安装或更新到 **1.4.1**，MP V3 ≥ 3.0.0。
2. MP 站点管理中维护思齐的 Cookie 和 User-Agent；也可在插件中填写覆盖 Cookie。凭据只发往固定 HTTPS 思齐源，接口不回显。
3. 启用插件，查看余额、库存、菜单和营业状态。
4. 配置中开启“后台自动经营”，使用 MP 原生 Cron 设置执行时间、是否补货、每日采购预算和保留魔力。默认 `0 8 * * *`，也可设 `0 8,12,18 * * *` 每天检查三次，时区跟随 MP。旧版时间自动迁移到等价 Cron；升级不自动开启托管。
5. 面板会显示最近后台检查、运行状态、采购预算占用及操作日志。需要手动操作时先暂停托管。

“保存后运行一次”会在保存后后台检查：未营业则开业并经营至闭店，营业中则接续服务，已闭店则结束；无需开启每日自动经营，开关会立即自动关闭。只保留右上角保存按钮。

默认执行时间 **08:00**，每日采购预算 **5,000 魔力**，补货后至少保留 **10,000 魔力**。预算只统计后台采购；手动采购需单独确认。更改配置、暂停再启用、重启和 Cookie 轮换不会清空当日预算。次日北京时间重置。

## MP 原生界面（1.3.0）

- 参考思齐农场的紧凑顶栏、轻量卡片、彩色开关与图标，配置页和餐厅面板使用同一套布局。
- 基础设置集中展示启用、通知和代理；自动化策略集中展示经营、补货与下馆子。三个用户名全部留空时仍为随机 3 人。
- 表单、开关、标签导航、表格和确认弹窗使用 MP 提供的 Vuetify 组件，继承宿主主题；按插件容器宽度调整列数，窄屏保留图标按钮的无障碍名称。
- 保留原配置字段、预算记录及任务状态；界面升级不修改已有托管和通知开关。

## 游戏规则与策略

规则依据站点说明和前端脚本核对。站点是动态游戏，解锁、价格、配方、顾客和计时均使用实时响应，不硬编码当前账号等级。

- 每天开业一次；开业后顾客开始消耗耐心。欢迎值影响顾客数、餐位、灶台、菜品和员工名额，HNR 与做种等级还会影响基础顾客数。其他用户到访可带来额外顾客。
- 顾客点什么菜，就要提供匹配成品。烹饪耗时和食材配方由菜单给出；更快完成服务有利于欢迎值。超时流失会损失欢迎值。具体奖励由站点结算，插件不推测或修改公式。
- 原网页的选菜、备料和烹饪计时在浏览器维护，服务端没有单独的烹饪接口。插件把这部分状态持久化在 MP，严格等待烹饪时间结束后才上菜。
- 每道菜先预留库存，避免并行灶台超领；完成服务时由站点结算食材和收益。工具可重复使用。取消备菜只释放本地预留，成品“归位”和“丢弃”都会按站点规则消耗食材。
- 上菜和顾客离席后，原餐位清理 **10 秒**，期间不再次上菜。可以在空闲灶台提前制作已出现的实际订单。
- 员工按同编号餐位工作；手动规则允许任意灶台向匹配顾客上菜。后台托管按手动操作规则调度所有已解锁灶台，无须额外买员工。
- 下馆子每日有次数限制，并可能要求二次确认。支持查询、推荐及手动到访，也可单独开启后台自动下馆子。

后台经营顺序：

1. 到开业时间，检查菜单工具和保守估计的库存缺口，确保当前预算和余额可承担最坏组合。这个估计把各食材最大用量乘以顾客数，可能高于最终实际需求；只检查、不提前采购。
2. 开业后按耐心截止时间处理实际订单，优先上已完成的匹配成品。到期顾客才提交离席。
3. 将未覆盖的订单分配给空闲灶台，同类在制/已完成菜品抵扣需求，避免重复做菜。食材够的订单同时开始烹饪。
4. 仅补实际订单所缺食材，逐次核对报价、每日余额和保留魔力。补货受限时，已经在烹饪的订单继续处理。
5. 每轮最多一次远端写入，不并发提交；营业期约每秒推进本地状态，完整读取缓存 5 秒，写入后刷新。未触发 Cron 时后台不访问站点；闭店后本次任务结束。状态页未营业、已闭店且无烹饪或清理任务时每 60 秒刷新一次；营业、烹饪或清理期间每 2 秒更新。页面切到后台暂停轮询，返回立即读取；手动刷新随时可用，空闲时不运行本地倒计时。
6. 闭店后等待下次 Cron，新增顾客也在设定时间检查。MP 必须保持运行；停机时间内顾客仍会消耗耐心。

托管不会自动雇佣员工或丢弃不匹配成品。现有成品会等待匹配订单；如所有灶台被不匹配成品占满，面板提示暂停后手动处理。

## 自动下馆子与通知（1.2.0）

- 独立“自动下馆子”开关；沿用 Cron 执行时间，有营业或在制菜品时优先等待经营完成。也可关闭自动经营、单独启用下馆子。
- 三个用户名输入框，全部留空时，从站点推荐列表随机挑选不同用户，每天最多成功到访 3 人。填写 1–3 人则只处理指定名单，空位不补随机人。重复用户名拒绝保存；本人、已到访或不可到访的目标跳过并记录原因。用户名不存在时只查询、不提交到访，不消耗次数，也不影响其余名单；当天不会重复尝试该错误用户名，修正成新用户名后可使用剩余次数。若误填为另一位真实用户，会按填写的用户名到访，请先在下馆子页查询核对。
- 按站点 `visits.count/limit/records` 扣除已用配额，后台进度持久化，重启、暂停再启用、换 Cookie 不会重复当天请求。未知请求保守占用一次配额，读回到访记录确认后继续；无法确认则保留锁，人工解锁也不重发原目标。
- 使用原站一键下馆子的 `confirm=yes` 规则，为目标餐馆增加顾客，不雇佣、不购买。保存开启即授权执行到访。每轮最多一次站点写入；找不到可用推荐时结束本次任务，下次 Cron 且至少 30 分钟后重查，随机模式每天最多尝试 12 位候选。指定目标被明确拒绝当天不重试，不换成其他用户。
- “发送运行通知”默认关闭。开启后使用 MP 的“插件”通知类型和现有渠道，分别汇总经营结果、下馆子结果；预算受限、结果不明及运行异常也会提示。同类通知每天最多一次，不逐单上菜推送，通知失败不阻断任务且当天不重发。需在 MP 配置接收“插件”通知。下馆子通知仅汇总已确认的到访数量和用户名，异常保留简短原因（最多 3 项，其余查看插件）；结果不明的预留次数不计为成功。闭店通知展示顾客数量、净收益与补货支出，仅在有顾客流失时显示流失数。完整站点回执仍保留在下馆子面板，升级不会重发当天已发送的通知。
- 升级时两个新增开关均默认关闭，原有经营参数和采购预算保持。下馆子面板展示当日后台结果和每位目标的处理情况；查询、随机推荐可在托管期间使用。

## 手动面板

- 概览、4 类状态厨房、食材与工具、菜品手册、员工雇佣和分配、下馆子、经营日志。
- 采购和雇佣显示实时费用并要求确认；报价超过确认预算时拒绝提交。
- 关闭托管时，可使用“运行已雇员工”，该旧模式仅在页面可见时运行，遵守同编号餐位服务规则。
- 开启自动经营或自动下馆子时，页面只读取后台状态，手动写接口也会拒绝，防止两个执行者互相抢单。

## 故障与恢复

每次远端写入前持久化请求意图、账号上下文、营业日期与操作前状态。响应不明时不重发原请求，而是读取完整站点状态：采购须同时匹配库存增量和余额扣款，开业/上菜/离席/到访须有相应状态或记录才能自动确认。跨账号、跨营业日期及缺少证据的旧记录不会自动解锁。

采购无法确认时单独隔离：保留预算占用、禁止继续采购及新营业，库存足够的订单继续烹饪和上菜，不再拖停整个厨房。长期断网或食材不足仍可能导致顾客流失，无法撤销站点已记录的流失。需要人工处理时，先核对余额、库存和顾客，再点击“已核对，解除锁定”；原请求不会重发。

厨房、清理时间、请求锁和最近 128 条请求编号跨重启保留。写入失败明确返回时，可在刷新状态后再次调度；被拒绝的采购至少等待 60 秒。营业中读取失败按 2–5 秒间隔重查，连接/读取超时分别为 3/5 秒；空闲只读查询为 5/15 秒，失败每 60 秒重查，最多三次后等待下个 Cron。HTTP 429 限流时至少等待 60 秒。暂停不撤销已发送的请求，但阻止下一步。

网页厨房与 MP 厨房不共享；同一账号请只在一个实例经营，不要同时运行网站员工自动化、插件分身和后台托管。Cookie 变化会重建本地厨房，跨日也清空旧厨房和清桌状态；不要在烹饪中途换账号。

### 状态页有余额，但提示读取失败

账号由各自的 Cookie 决定，没有固定用户名或用户 ID。插件配置中的覆盖 Cookie 优先于 MP 站点 Cookie；覆盖字段留空保存会保留旧值，要切回 MP 站点凭据需使用清除覆盖 Cookie。请求使用 MP 站点的 User-Agent；插件代理开关独立控制是否使用 MP 代理，关闭时仍可能使用进程的环境代理。

状态页与后台共用凭据和请求逻辑，但查看状态成功不代表下一次请求或下馆子查询成功；失败时页面会保留最后成功读取的余额、库存。1.4.0 的“读取站点失败，请检查网络、Cookie 和代理”同时覆盖网络异常及非 JSON 响应，不能据此认定 Cookie 失效。

1.4.1 会注明失败操作（状态、指定餐馆、随机餐馆）、连接/读取超时、代理/TLS 错误、HTTP 状态或 HTML/JSON 响应问题，并只显示 Cookie 来源与网络设置，不记录凭据、响应正文或代理密码。短暂连接/读取失败或 HTTP 5xx/429 连续三次才发送“需要处理”，前两次显示自动重查；登录/权限、验证页和格式异常立即提示。所有操作仍不在请求层盲目重试，写入结果不明时继续原有读回核对。

## 接口

全部路由使用 MP Bearer 认证。基础路径 `/api/v1/plugin/SiqiRestaurant`，分身使用运行态插件 ID。

| 路由 | 用途 |
| --- | --- |
| GET `/state` | 餐厅、厨房、清桌、自动经营状态和日志 |
| POST `/refresh` | 强制刷新状态 |
| GET/POST `/config` | 安全读取/更新配置，不回显 Cookie，保存同步宿主调度 |
| POST `/action` | 受限手动操作；`action`、`args`、唯一 `request_id` |
| POST `/tick` | 旧页面员工模式；托管开启时只读 |
| POST `/resolve` | `acknowledged: true`，核对后解除未知写入锁 |

后台调度复用厨房状态校验，不提供绕过计时的原始 `serve_customer` 接口。
